# Final Project Summary

## Project Aim

The aim of this project was to build a custom SystemVerilog FPGA soft-core CPU and use it as a practical study of digital design, verification, FPGA implementation, timing closure, resource usage and performance trade-offs.

The project started from small verified RTL modules and progressed through integrated CPU cores, memory-system changes, pipelining, FPGA bring-up, hardware profiling and high-frequency board measurement.

## Final Headline Result

Phase 17E physically measured approximately 100 MIPS on the Digilent Basys 3 FPGA.

The final hardware milestone used:

- CPU: original Phase 13 forward-timing five-stage pipeline
- Clock: 115.000 MHz generated by an RTL-instantiated MMCM
- Measurement: FPGA-resident retired-instruction MIPS counter
- Display: Basys 3 four-digit 7-segment display
- Observed MIPS display: `0100`

This is the best real FPGA-measured result in the project. It physically confirms the Phase 17D timing-supported estimate that the original Phase 13 pipeline could reach approximately 100 MIPS when clocked above 100 MHz.

## Custom ISA Summary

The project uses a compact custom 32-bit instruction format:

| Field | Bits |
| --- | --- |
| opcode | `[31:28]` |
| rd | `[27:23]` |
| rs1 | `[22:18]` |
| rs2 | `[17:13]` |
| imm13 | `[12:0]` |

Supported instructions:

- Arithmetic/logical: NOP, ADD, SUB, AND, OR, XOR, ADDI
- Memory: LOAD, STORE
- Control flow: BEQ, JUMP

Key architectural rules:

- `x0` is hardwired to zero.
- `imm13` is sign-extended.
- BEQ and JUMP use PC-relative word offsets.
- Invalid opcodes are safe and do not write registers or memory.

## Architecture Evolution

The CPU evolved through several implementation styles:

| Stage | Summary |
| --- | --- |
| Early single-cycle-style CPU | Simple integrated custom-ISA CPU, strong CPI but poor timing closure |
| Multi-cycle CPU | Timing-clean 100 MHz FPGA path with higher CPI |
| BRAM-aware multi-cycle CPU | Synchronous memory structure for realistic FPGA block RAM inference |
| Prefetch CPU | Reduced BRAM latency penalty |
| Control-flow optimised prefetch CPU | Improved multi-cycle control-flow performance |
| Phase 12 five-stage pipeline | Separate full pipeline with forwarding, hazards and retirement |
| Phase 13 forwarding/timing pipeline | Best fixed-100 MHz board-measured path |
| Phase 14 six-stage pipeline | Higher timing potential but worse CPI on the measured workload |
| Phase 17 profiling and MMCM test | Hardware profiling plus 115 MHz physical MIPS measurement |

The most important architectural lesson was that deeper pipelining did not automatically improve real board MIPS. The Phase 14G six-stage CPU closed timing at a much higher estimated clock, but its CPI was worse at the fixed 100 MHz board clock. The Phase 13 five-stage path had better board CPI, and the Phase 17E MMCM test used that advantage to physically reach approximately 100 MIPS.

## Verification Strategy

Verification was built up incrementally:

- Self-checking Vivado XSim testbenches for individual modules.
- Program-level tests for the custom ISA.
- Full custom-ISA regression for integrated CPU variants.
- Focused tests for pipeline movement, forwarding, load-use hazards, control-flow redirects, wrong-path side effects and invalid-opcode safety.
- Vivado synthesis and implementation reports for timing, utilisation, BRAM inference and bitstream generation.
- Physical Basys 3 measurements using LEDs and 7-segment display counters.
- Phase 18 benchmark alignment using the same instruction-memory image and retire signal in XSim and the FPGA wrapper.

The project used separate implementation paths for experimental CPU variants so that verified baselines were not overwritten.

## FPGA Bring-Up

Hardware bring-up progressed from simple observability to direct performance measurement:

- LED debug wrappers showed program and pipeline state.
- Slow-enable stepping made CPU progress visible on the board.
- Sticky event LEDs latched short retire, register-write, memory-write and redirect pulses for physical evidence.
- The Phase 16A MIPS counter displayed 100 MHz hardware throughput on the Basys 3 7-segment display.
- Phase 17A/17B extended the Phase 13 hardware profiler with MIPS, CPI and bottleneck display modes.
- Phase 17E used an MMCM-generated 115 MHz CPU clock and displayed the final `0100` MIPS result.
- Phase 18 reused the 115 MHz measurement wrapper with `programs/final_benchmark.mem` so simulation and FPGA can be compared on the same workload.

| Category | Result |
| --- | ---: |
| Best fixed 100 MHz hardware result | Phase 13, approximately 87 MIPS |
| Best high-frequency measured hardware result | Phase 17E, approximately 100 MIPS at 115 MHz |
| Best timing-estimated result | Phase 14G, approximately 101.8 MIPS |
| Phase 17B CPI x100 | `0115` |
| Phase 17B control flush x100 | `1250` |
| Phase 17E MIPS display | `0100` |
| Phase 18 aligned simulation prediction | approximately 93.0 MIPS at 115 MHz |
| Phase 18 aligned board display | `0093` |

Important distinction:

- Phase 17E is the best real FPGA-measured result.
- Phase 14G remains the best timing-estimated result.
- Phase 14G's approximately 101.8 MIPS result has not been physically measured at 166.667 MHz.

## Main Engineering Lessons

- CPI and Fmax must be considered together; neither metric is sufficient alone.
- Deeper pipelining improved timing potential but increased CPI on the measured workload.
- FPGA block RAM timing must be handled explicitly.
- Control hazards were the dominant measured Phase 13 CPI bottleneck at the 100 MHz board clock.
- A timing-clean estimate is not the same as a physical board measurement.
- Hardware profiling is valuable because it prevents guessing which optimisation matters.
- The MMCM high-frequency test physically confirmed the 100 MIPS milestone without changing the original Phase 13 CPU RTL.
- Benchmark alignment matters: Phase 18 showed that changing the instruction-memory program changes CPI and therefore expected board MIPS, even with the same CPU and same clock.

## Comparison Class

The final CPU is a custom educational FPGA soft-core. It should be compared carefully:

- It is faster in raw MIPS than classic Arduino Uno/Nano-class 16 MHz AVR boards.
- It is comparable to some simple microcontroller-class processors for straight-line integer instruction throughput.
- It is not comparable to Raspberry Pi application processors, which use GHz multi-core CPUs, caches, memory management, operating systems and far more complex microarchitectures.

## Limitations

- The ISA is intentionally simple and custom.
- There are no interrupts, caches, UART, compiler, operating system or external memory interface.
- The hardware MIPS value depends on the program loaded into instruction memory.
- The 7-segment display reports integer MIPS, so fractional precision is lost.
- The Phase 17E result uses the FPGA demo workload, not a standard benchmark suite.
- Phase 14G's approximately 101.8 MIPS value is timing-estimated rather than physically measured.
- Phase 17E has small positive timing slack at 115 MHz, so further clock increases need fresh timing and board validation.
